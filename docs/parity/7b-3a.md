Engine behaviour changed for Go parity while porting (each covered by the ported rows and by
gadk-engine tests; recorded here because the plugin's rows depend on it):
- The LLM flow runs the on-model-error callbacks with Go's `ctx.Err()` (`context canceled`, or
  `context deadline exceeded` on a deadline) when the agent's context ends during a model call
  (Go's model returns `ctx.Err()`), so the plugin writes Go's `LLM_ERROR` row; a model item that is
  already ready wins over the cancellation, as Go's flow does not check its context between the
  model's responses (`crates/gadk-engine/src/llm/flow.rs`, `Flow::call_model`).
- The plugin's identities read `Context::context_path()` (Go `contextPath`), so a workflow node
  agent and a tool-run helper carry their node / enclosing path (`plugin/rows.rs`, `identity_of`).
- A workflow node started again while its earlier activation still runs releases the earlier
  activation's cancel guard instead of cancelling it (Go's `scheduler.go` overwrites the entry;
  `workflow/scheduler.rs`, `start_node`).
- Early stop is Go's synchronous unwinding, not an abort: nothing the invocation started is
  aborted any more when the consumer drops the runner's stream. A per-invocation teardown
  registry (`gadk_agent::Teardowns`, installed by the runner) collects the work components were
  dropped with, and the runner's `InvocationGuard` awaits it before the after-run callbacks on
  every path (at a yield with the invocation's token still live). A ParallelAgent dropped early
  acks the event the reader stopped on, cancels its group plainly and registers its funnel, which
  waits for every branch (Go `parallelagent` #1186); the workflow `Scheduler` dropped by a gone
  consumer releases the pending handshake, cancels its node tasks and registers their drain (Go
  `scheduler.go`'s consumer-gone drain); a tool dispatch dropped early cancels its calls' scope
  plainly (Go: the caller's cancel; a tool waiting on its context ends, so after-run cannot hang
  on it) and moves the task runner's future into a registered teardown, so running tool calls
  finish and reach their after-tool / on-tool-error callbacks (Go `platform.RunTasks` waits for
  every task) — a tool that ignores cancellation now runs to completion, as in Go; the live flow's event stream, dropped, cancels
  `done` and detaches its session task (not registered: Go's `RunLive` after-run does not wait for
  the session goroutine), so an in-flight live tool call finishes and writes its late rows. Three
  Rust-only engine tests that asserted the old abort were rewritten to this behaviour.

Accepted divergences (each annotated `// Divergence (ledger 7b-3a)` where it lives; 15):

Tool origins and contexts:
- Go's `classifyADKToolType` classifies a tool by its package path and type name, so a user tool whose package or type name contains "toolbox" / "skill" is TOOLBOX / SKILL and a `functiontool` value is LOCAL; gadk tools declare their kind through `Tool::origin_kind` (gadk-engine's function tools LOCAL, overridable by `FunctionToolConfig.origin`; gadk-tools' skill tools SKILL; the MCP tool MCP; the agent tools SUB_AGENT / A2A from `origin_agent`; the transfer tool TRANSFER_AGENT / TRANSFER_A2A from its supported agents, `Tool::origin_agents`), and a user tool that declares none is UNKNOWN — `crates/gadk-agentanalytics/src/events.rs` (`tool_origin_of`).
- Go reads whatever OpenTelemetry span the caller's `context.Context` carries, so the rows of a run started under a caller's span join that trace (`attributes.otel`, the adopted trace ID); gadk reads only the nearest span gadk-telemetry's bridge marks as an ADK span (`gadk_engine::telemetry::current_span_ids`), and the bridge starts a new trace under a non-ADK span, so a caller's span is never inherited — `crates/gadk-agentanalytics/src/trace/mod.rs` (`CallbackCtx::from_context`).
- Go's A2A lookup for a transfer or agent tool reflects over the unwrapped tool's `agent` / `supportedAgents` / `SubAgents` / `RootAgent` fields; gadk searches the agents the tool exposes through the typed accessor `Tool::origin_agents()`, so a user tool that does not override it is searched through `origin_agent()` only — `crates/gadk-agentanalytics/src/events.rs` (`find_agent_a2a_by_name`).
- Go dereferences the plugin's trace manager unconditionally when it emits session-event signal rows (a plugin without one panics into `recoverCallback` and drops the row); gadk uses an empty row span when the plugin has no trace manager — `crates/gadk-agentanalytics/src/events.rs` (`emit_session_event_signals`).

Rows:
- `attributes.adk.adk_version` is gadk-agentanalytics' crate version (every gadk crate shares the workspace version), where Go reads the linked ADK module's version from `debug.ReadBuildInfo` (empty for a development build) — `crates/gadk-agentanalytics/src/plugin/version.rs` (module doc).
- `AGENT_STARTING`'s agent config: Go's reflection also reads the config through an exported `Agent` field of a user agent that wraps an LLM agent; gadk reads only an LLM agent's own config (`gadk_engine::llm::llm_agent_config`) — `crates/gadk-agentanalytics/src/plugin/rows.rs` (`agent_starting_data`).
- A content formatter receives the payload's JSON (7b-1's `ContentFormatter` is `Fn(&Value, &str)`): `Content` / `LlmResponse` as serde JSON, `LlmRequest` as Go's `json.Marshal(model.LLMRequest)` (`{"Model","Contents","Config"}`); Go hands the typed value and keeps whatever Go type the formatter returns. An unchanged result keeps the typed payload; a changed one that still reads back as the payload's type (re-serializing to the same JSON) is used as that type; anything else is a JSON payload (no `content_parts`) — `crates/gadk-agentanalytics/src/plugin/rows.rs` (`payload_json`).

Plugin lifecycle and recovery:
- A recovered panic's `%T` in `agentanalytics: dropped <type> event: recovered panic of type <T>` is `string` for `&str` / `String` payloads, else `unknown` (Rust has no runtime type name of a panic value), and Rust's panic hook still reports the panic before it is caught, where Go's `recover` is silent — `crates/gadk-agentanalytics/src/plugin/filter.rs` (`AnalyticsPlugin::recover_callback`).
- Go's `onUserMessage`, `beforeRun` and `beforeModel` recover only inside their `logEvent`; gadk also guards those three callback bodies (`USER_MESSAGE_RECEIVED`, `INVOCATION_STARTING`, `LLM_REQUEST`), so a panic outside a row (e.g. in the user-message signal rows or a trace-manager call) is counted as a dropped row instead of reaching the run — `crates/gadk-agentanalytics/src/plugin/callbacks.rs` (`AnalyticsPlugin::guard`).
- Go's `CloseFunc` has no once-guard (a second `Close` closes the processor, offloader and clients again and reports their errors); gadk runs the close sequence once, on a task of its own that every call awaits, and a second close returns the first call's result. A `PluginManager` close timeout drops only a waiter, so the drain still delivers every row — `crates/gadk-agentanalytics/src/plugin/mod.rs` (`close_fn`).

Goroutine attribution (7b-3b):
- Go's goroutine identity comes from `runtime.Stack`: the goroutine's id, the function whose `go` statement created it (`schedulerCreator`, `errgroupCreator`, …) and the frame shape that tells a workflow-node or ParallelWorker attempt (`attemptSiteOfTrace`); gadk reads fiber ids the engine sets where Go starts those goroutines, its creators are the `gadk_agent::fiber` constants (`SCHEDULER_CREATOR`, `ERRGROUP_CREATOR`, `PARALLEL_WORKER_CREATOR`, `LIVE_SESSION_CREATOR`) and the attempt site is the engine's per-fiber slot (`with_attempt`, claimed by the first agent run on the fiber for its before-agent callbacks), not a stack-frame match, so only the engine's spawn sites are recognised — `crates/gadk-agentanalytics/src/trace/settle.rs` (`current_goroutine`).
- Go always has a goroutine id; gadk's fallback id of a task without a fiber is its tokio task id (`(1 << 63) | id`, unique only among running tasks), and outside any task and fiber the id is 0 — `crates/gadk-agent/src/fiber.rs` (`current`).
- A goroutine keeps its id wherever its code runs; a started agent stream moved to another task keeps its fiber only when it is wrapped in a `FiberStream`, and agent streams polled concurrently in one task share that task's fiber (Go would run them on separate goroutines). The engine never moves a started agent stream across tasks nor joins several in one task. A fiber's attempt slot assumes its claims are nested (LIFO); a teardown task re-enters its dropper's fiber (`spawn_teardown`), so two tasks can claim on one fiber at once and an out-of-order restore can leave a stale attempt mark, seen only by attribution outside a claim — `crates/gadk-agent/src/fiber.rs` (`FiberStream`).
- A Go consumer that stops reading early unwinds the iterator on its own goroutine — teardown, the deferred `RunAfterRunCallback`, compaction — before its `break` returns; a dropped Rust stream cannot block its dropper, so the runner runs that work on a spawned task re-entering the consumer's fiber (the after-run callbacks see Go's goroutine), which may overlap the consumer's next work (`TestRunner_StoppedStreamsKeepCompletedRunsBounded` waits for it) — `crates/gadk-engine/src/runner/compaction.rs` (`InvocationGuard::drop`).

Flow cancellation (7b-3b):
- Go's `generateContent` always opens the `generate_content` span and calls the model, which observes the ended context and yields `ctx.Err()` inside the span; gadk's models do not see the context, so a model call whose context has already ended is skipped with its span, and the flow runs the on-model-error callbacks with `ctx.Err()` itself (no `generate_content` span is recorded for that call) — `crates/gadk-engine/src/llm/flow.rs` (`Flow::call_model`).

Not annotated (no Go-observable effect, or not applicable):
- Go's goroutines are fibers (`gadk_agent::fiber`): a task-local scope carrying an id, a spawn origin (creator, parent id) and an attempt slot. The engine starts a child fiber where Go starts a goroutine the trace manager recognises — a workflow node activation (`SCHEDULER_CREATOR`, from the fiber polling the workflow), a ParallelAgent branch (`ERRGROUP_CREATOR`), a ParallelWorker item (`PARALLEL_WORKER_CREATOR`) and the live session (`LIVE_SESSION_CREATOR`); the runner's `run` / `run_live` streams run on the consumer's fiber (a fresh root fiber when the consumer has none), which Go's iterator shares with its consumer; any other task (Go's anonymous `go func` in a test or user agent, a tool call on the default `TaskRunner`) has a fallback fiber with a zero origin, as Go's anonymous creators match no creator constant. An `AgentNode` activation is marked `AttemptSite::Node` and a ParallelWorker item `AttemptSite::Worker`; the first agent run on the fiber claims the mark for its before-agent callbacks, where Go matches the stack frames of the node / worker body. The fallback-id and moved-stream limits and the spawned early-stop after-run are the 7b-3b divergences above. A ported direct test that compares with Go's test goroutine runs its body on a root fiber (`attr_support::on_test_goroutine`; adapted rows); Go's `iter.Pull` child of `TestAttemptSitesMatchADK` has no gadk counterpart.
- A `ParallelWorker` stream dropped mid-await aborts its item tasks, where Go's `Run` keeps ranging its results until `wg.Wait`; the engine never drops it mid-await (the workflow scheduler drains its node tasks instead of dropping them), so only a direct user of the node's stream can observe it (`workflow/nodes/parallel_worker.rs`, `run` doc).
- A raw `CancellationToken::cancel()` by user code records no cause: `cause()` then reads the nearest cause recorded on a cancelled enclosing scope, else `Canceled`. Unreachable in Go, which cancels a context only through its `CancelFunc` / `CancelCauseFunc`; gadk's own cancellations go through `CancelGuard` / `cancel_with_cause`, which record Go's cause.
- `Runner::run` / `run_live` take no caller context (gadk's runner API, all sub-projects): the invocation's token is the root of the run's cancel scope and is cancelled when the stream ends or is dropped, where Go's caller context (e.g. `t.Context()`) outlives the run. Ports whose Go test cancels or outlives the caller's context are adapted rows (a plugin or the consumer cancels the invocation's context; a helper detached past the run gets a token of its own).
- Go's activation pointer identity (`activationKey`) is `gadk_agent::ActivationId` (assigned where an `ended` flag is created, kept by deltas); Go `map[agent.Agent]…` keys are `Arc` data addresses holding the `Arc`s; `container/list` (the completed-run LRU) is a `VecDeque` with generations (same order); `contextParentMap`'s map iteration is the parent map's tree order (Go's is random); the weak-pointer plugin registry is the plugin's typed state slot (`Plugin::state`), dropped with the plugin.
- Go's `orZero` guards around agent and session accessors: gadk contexts always have an agent and a session and the accessors do not panic; where agent code runs (`running_agent_children`, `agent_type_of`, A2A lookups, the state snapshot) the port wraps it in `catch_unwind` like Go's `recover`.
- `write_event` without a processor drops the row silently (Go calls `Append` on a nil processor, panics and recovers with a `runtime.Error` type in the log line); only Go's test literals reach it.
- Callback bodies run synchronously when gadk calls the callback, before its future is returned, so every trace-manager call and every `BatchProcessor::append` happens in Go's order even though gadk's callbacks are async; after-run then awaits the run-end flush.
- Go's typed `map[string]any` attribute values (`*genai.Schema`, `float32` settings, label maps, grounding metadata, …) are their 7b-1 sanitized JSON trees, so the JSON written is Go's (a `float32` keeps its 32-bit text).
- The ported Go tests build one gadk invocation context per Go `mockInvocationContext` (`support::MockCtx` caches it per identity), since every gadk ADK context carries an activation where Go's mock has none; Go's ambient-span injection is `CallbackCtx::with_span` on the callback bodies (`support::SpanPlugin`); Go's goroutines in tests are threads or tasks; Go's GC / weak-pointer checks are `Arc` / `Weak` counts (adapted rows).
